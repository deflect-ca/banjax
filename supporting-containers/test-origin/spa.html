How to test

  1. Open this page through the edge at http://localhost/spa (port 8080 is the origin directly, without banjax). Use localhost or https: otherwise the browser sends no Sec-Fetch-* headers, and only the XHR button that sends X-Requested-With is recognised as a request that cannot show a page.
  2. Leave polling on. Calls show OK.
  3. Challenge this site (commands below, under "Trigger a challenge"). The challenge type decides the challenge field of the JSON: sha_inv, altcha or altcha_click.
  4. Click through the test points. Expected results while challenged:
    • fetch, XHR, POST, no-cors, img, script, stylesheet: 403 JSON (for img, script and stylesheet the page can only see load/error and the Resource Timing status). Not counted toward a ban, so polling carries on.
    • iframe and reload: the HTML challenge page (429), counted toward the failed-challenge ban.
    • CORS preflight: never challenged (CORSPreflightException).
  5. Click Reload to verify (or tick auto-reload) to get the challenge as a page, solve it, and come back: calls are OK again.

Three failed HTML challenges in 10 seconds from one IP get that IP banned. A browser on the same machine as curl shares that IP: if everything hangs, see scripts/dev banned and scripts/dev unban <ip>.

Known gap: cross-origin calls to a sibling host cannot recover from a challenge

A page on localhost calling www.localhost (or the other way round) can fail when the API host is challenged. The challenge cookie is scoped to the host, and banjax gives CORS headers only to an Origin equal to the requested host, so the sibling origin gets none. The script then sees a network error (a TypeError), not the JSON, and cannot tell a challenge from an outage. Test point 10 shows this: challenge www.localhost (command below) and run it.
